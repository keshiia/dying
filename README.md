# 青知法苑 · 青少年普法智能体

> 让法治成为青春的底色 —— 面向中学生的互动式 + 智能体个性化普法平台

---

## 一、作品简介

### 1.1 项目背景

随着互联网在青少年群体中的普及，校园欺凌、网络诈骗、个人信息泄露、消费维权、交通安全、毒品诱导等法律问题日益突出。然而，传统的普法教育多停留在法律条文的宣讲层面，形式单一、内容枯燥，学生难以产生学习兴趣，学习效果无法量化评估，教师的"教"与学生的"学"都缺乏有效的工具支撑。

本项目"青知法苑"面向中学生与法治教师，构建一个**互动式学习 + 智能体个性化**的普法平台：以模拟法庭、案件侦查、闯关挑战、普法漫画等形式降低学习门槛；并内置一套轻量智能体系统，通过持续分析学生的学习行为数据，生成**个性化画像、能力轴诊断、智能推荐、错题复盘与每周目标**，让法治教育从"千人一面"走向"千人千面"。

此外，平台内置**对话风险预警**：学生在与 AI 助手交流时，系统同步识别可能的风险信号并实时推送给教师，把"教师发现问题学生"从被动等待变为主动预警，让风险干预得以前置。

### 1.2 核心功能

#### 学生端

### 1.3 学习内容覆盖

平台涵盖青少年日常生活中最常见的 6 大法律主题：

1. **校园安全** —— 校园欺凌的识别与应对、受教育权保护
2. **网络安全** —— 网络诈骗防范、个人信息保护、网络言论边界
3. **家庭权益** —— 未成年人家庭保护、家庭暴力的识别
4. **消费维权** —— 网购维权、消费者权利、预付卡退款
5. **交通安全** —— 交通法规、骑行安全、事故处理
6. **禁毒教育** —— 毒品危害认知、识别与拒绝技巧

每个主题下设 10 个关卡（共 60 关），题目类型包括：

- **单选题（SINGLE）**：标准四选一
- **判断题（TRUE_FALSE）**：判断对错
- **情境题（SCENARIO）**：基于真实场景的案例分析

所有题目均配有详细解析与法条出处，答错后可查看正确答案与法律依据。

> **题库构成说明**：60 个关卡中，24 关及其 123 道题为按主题逐题手写；其余 36 关（每主题第 5-10 关）的 180 道题由场景参数**模板化生成**——每题由主题、风险行为、安全行为、法条依据、情景五个字段插值产出，用 60 行模板表达完 6 主题 × 10 关的覆盖，保证知识体系完整且口径一致。

题库覆盖《未成年人保护法》《民法典》《网络安全法》《个人信息保护法》《家庭教育促进法》《消费者权益保护法》《道路交通安全法》《禁毒法》《治安管理处罚法》《广告法》等 **12 部法律法规**。

### 1.4 成长激励机制

- **经验值系统（XP）**：闯关得分 ≥ 60 获得对应 XP，阅读漫画获得 XP，通关模拟法庭/案件侦查按表现发放 XP
- **按最佳成绩差额结算（防刷分）**：每个关卡、每个游戏案件都只按**历史最好成绩**结算，重复提交只补发差额。既保证反复刷同一关不会无限刷 XP，也不让认真重刷提高成绩的学生吃亏；游戏侧另有完成度钳制与"0 分不保底发放"
- **漫画双档奖励**：读完整篇保底 +10 XP（低门槛入门的定位不动摇），读后总结题答对另发 +5 XP
- **等级系统**：每 100 XP 升一级，等级对应称号（法律小白 → 初级法律达人 → 法律知识进阶 → 法律小专家 → 法律小达人）
- **成就徽章**：9 枚可解锁徽章，涵盖学习起步、连续打卡、高分挑战、关卡通关等维度，仅在新解锁时播放庆祝动画
- **顺序解锁**：主题内关卡按顺序解锁，保证知识体系完整
- **错题复习**：得分低于 100 分的关卡进入"待复习"列表，鼓励巩固薄弱环节

### 1.5 智能体个性化（本项目核心特色）

在常规学习功能之上，平台内置了一套轻量智能体系统，统一以「**青知智能体**」的身份出现在结算页复盘卡、侧边栏入口与对话页，围绕学生数据提供四项个性化能力：

| 能力 | 说明 |
|------|------|
| **六维学习画像** | 按 6 大主题统计掌握度，识别薄弱点、优势项与学习风格，以雷达图直观呈现 |
| **智能推荐** | 根据画像推荐"下一步学什么"并给出理由，并可直接跳转到具体篇目或案件 |
| **智能错题复盘** | 基于逐题作答记录统计真实题型正确率，识别共性错误模式，生成针对性改进建议 |
| **每周学习目标** | 基于学习节奏自动拆解本周目标（完成关卡 / 错题复盘 / 每日打卡）并跟踪进度 |

#### 1.5.1 六条能力轴与结算页诊断

除主题画像外，平台另设一套**能力轴**坐标系，用于回答"为什么弱"：

观察取证 · 信息获取 · 证据审查 · 逻辑推理 · 法律适用 · 表达论辩

这六条轴并非凭空设计，而是从模拟法庭与案件侦查**原本算完即弃的评分维度**收敛而来。学生在游戏中的每次操作都会沉淀为细粒度信号（漏了哪条线索、漏的是哪一类证据、哪道题选错），结算时由诊断引擎产出**可点击的复盘卡**：

- 指出具体短板并**举证到具体线索**（"「观察取证」本局 6/9，漏掉的是「走廊监控」这类"）
- 识别**类型盲区**（"你漏了 2 条电子类证据——手机、电脑、监控这类东西你都没主动查"）
- 识别**跨局重复**（"最近 3 局里有 2 局这一项都不达标——不是偶然"）
- **先肯定强项**再指出短板，样本不足的轴显示"样本不足"而非 0 分
- 给出可以直接跳转的推荐（去看某篇漫画 / 换个游戏场景检验同一能力）

卡片在结算页**默认折叠**——结算是"案件告破！"的庆祝时刻，折成一行让想被诊断的人自己点开，不打扰不想看的人。

#### 1.5.2 诊断的生成方式：规则出结论，模型只出措辞

诊断结论**全部由确定性规则引擎计算**，大模型只被允许把已算好的结构改写成一句话，且明确禁止引入结构中不存在的线索名、数字或结论。这样保证：

- **可复现**——同一份数据每次诊断一致，演示可重放；
- **可解释**——被问"凭什么说他观察力弱"，能指回具体是哪条能力轴、漏了哪条线索；
- **不编造**——纯模型诊断会说出案件里根本不存在的线索，这在教育产品中不可接受。

模型超时、上游报错、输出不合格三种情况一律退回模板文案，闭环在任何情况下都成立。**未配置 AI Key 时，整套诊断与个性化能力依然完整可用**。

AI 对话助手同样在每次对话时自动注入用户画像、学习进度、历史提问，以及**从复盘卡"追问"按钮带过来的案件与短板上下文**，实现带记忆的个性化问答。

### 1.6 风险预警（教师端）

学生在与 AI 助手对话时，系统会同步识别可能的风险信号，并将需要关注的情况实时推送到教师端。

**两级判定，各司其职：**

| 层级 | 机制 | 特点 |
|------|------|------|
| **第一级：同步窄规则** | 区分自指性危机表达（"我不想活了"）与可能只是法律学习的表达（"自杀违法吗""被打还手算正当防卫吗"），命中即在 AI 回复最前面**由代码强制拼接**求助卡片（监护人 / 老师 / **110** / **12348**） | 不经过模型、不依赖 API Key，真正救命的部分必须确定 |
| **第二级：异步模型判定** | 产出风险类型、等级（高 / 需关注 / 轻微）、给教师的沟通建议，异步执行不拖慢学生回复 | 能发现"持续情绪低落""被孤立""家庭冲突"这类**没有硬关键词**的心理风险 |

**针对普法场景的专门优化**：学生在普法平台上经常在问法条、做假设推演，这是本场景特有的误报来源。判定提示词明确要求区分"描述亲身处境"与"了解法律规定"，并给出正反示例。**级别下限由窄规则锁死**——模型可以补充描述，但没有权力把规则判定的高危降级。

**面向教师体验的设计**：同一学生同一类型的风险在 24 小时内**聚合累加**而非逐条新建，避免学生连发几条就把教师端刷满、反而导致整个预警面板被忽略；聚合时原句取"更严重的那个"，平级保留先出现的。教师端显示风险类型、等级、学生、触发原句、相对时间与处置状态，支持填写沟通记录、标记已处理或误报。

### 3.2 Docker 部署（推荐）

**第一步：准备项目文件**

将项目源码（或已构建的 Docker 镜像 tar 包）放到服务器 `/opt/legal-for-teen/`。

**第二步：配置环境变量**

创建 `.env` 文件：

```env
# MySQL
MYSQL_ROOT_PASSWORD=root123
MYSQL_DATABASE=lft_db
MYSQL_USER=lft_user
MYSQL_PASSWORD=lft_pass123

# JWT（生产环境务必更换为随机长字符串）
JWT_SECRET=替换为一个随机字符串
JWT_EXPIRES_IN=7d

# CORS（改为你的服务器 IP 或域名）
FRONTEND_ORIGIN=http://你的服务器IP

# AI 对话助手 / 诊断措辞 / 风险判定（可选，不配置则走内置兜底文案）
OPENAI_API_KEY=你的API密钥
OPENAI_MODEL=mimo-v2.5
OPENAI_BASE_URL=https://api.xiaomimimo.com
```

**第三步：启动服务**

```bash
docker compose up -d
```

首次启动会自动：
1. 构建前端、后端镜像（或直接使用已加载的镜像）；
2. 后端自动执行 `prisma migrate deploy` 建表；
3. 后端自动执行 `prisma db seed`（幂等，可重复执行）填充题库与测试账号；
4. 启动 Nginx 前端，反向代理 `/api` 到后端。

**第四步：访问**

| 服务 | 地址 |
|------|------|
| 前端页面 | http://localhost 或 http://你的服务器IP |
| 后端健康检查 | http://你的服务器IP/api/health（经前端 nginx 反代；本地开发也可直接访问 http://localhost:3001/api/health） |

**种子账号：**

| 角色 | 邮箱 | 密码 |

| 教师 | teacher@example.com | Teacher123! |

种子数据还会创建一个示例班级「高一(1)班」，邀请码 **`LEGAL8K8K`**，上述学生账号已是该班成员，教师账号是该班班主任，班内另有一条已布置的闯关任务——**登录后即可直接演示教师端看板与风险预警**，无需手动建班。

**常用 Docker 命令：**

```bash
docker compose ps              # 查看服务状态
docker compose logs -f backend # 查看后端日志
docker compose restart         # 重启所有服务

```

> **部署提示**：仓库内有两份 compose，端口策略不同——
> - 根目录 `docker-compose.yml`（本地开发）**发布** db(3306) 与 backend(3001)，以便在宿主机运行 `npm run dev`（Vite 的 `/api` 代理指向 `localhost:3001`）以及直接执行 prisma 命令；

>
> 部署到有公网 IP 的服务器时请使用 `deploy/` 下的配置，避免数据库直接暴露到公网。

## 四、设计思路

### 4.1 整体架构

项目采用**前后端分离架构**，通过 Docker 容器化部署：

- **前端**：React 单页应用（SPA），Vite 构建，Tailwind CSS 响应式设计；生产环境由 Nginx 提供静态文件服务与 SPA fallback
- **后端**：Express.js RESTful API，Prisma ORM 操作 MySQL，含认证、业务与智能体分析路由
- **数据库**：MySQL 8.x，独立容器运行
- **部署**：Docker Compose 编排三个容器，Nginx 反向代理 `/api` 请求到后端，实现同源访问

```
                           ┌─────────────────┐
                           │   浏览器访问     │
                           │  http://localhost │
                           └────────┬────────┘
                                    │
                           ┌────────▼────────┐
                           │   frontend       │
                           │   (Nginx:80)     │
                           │  / → index.html  │
                           │  /api/* → proxy  │
                           └────────┬────────┘
                                    │
                           ┌────────▼────────┐
                           │   backend        │
                           │  (Express:3001)  │
                           │   RESTful API    │
                           └────────┬────────┘
                                    │
                           ┌────────▼────────┐
                           │   MySQL 8.x      │
                           │   (db:3306)      │
                           └─────────────────┘
```

### 4.2 智能体个性化架构

智能体功能由后端模块在容器内离线计算，不依赖外部大模型服务：

```
学生行为数据（答题 / 进度 / 漫画 / 游戏）
        │
        ├─────────────────────────────┐
        ▼                             ▼
学生画像引擎（studentProfile.ts）   能力轴重算（agentDiagnosis.ts）
   · 6 主题掌握度 + 趋势识别           · 从 GameResult.detail 与
   · 按题型聚合薄弱点                     ComicRead.quizCorrect 重算
   · 学习风格识别                       · 6 条能力轴，存计数而非百分比
   · 惰性更新（5 分钟缓存）             · 天然幂等、可重放
        │                             │
        ├──► 六维雷达图                ▼
        ├──► 推荐规则引擎 → 智能推荐区  智能体诊断引擎
        ├──► 错题聚合分析 → 错题复盘     · 单局弱项 / 类型盲区 / 跨局重复
        └──► 每周目标生成 → 目标卡片     · 强项确认（先肯定再指出短板）
                                      · 跨模块呼应 → 可点击的推荐
                                            │
                                            ├──► 规则产出结构化诊断
                                            └──► LLM 仅改写标题一句话
                                                 （失败 → 模板兜底）
                                            │
                                            ▼
                              结算页折叠复盘卡（InterventionCard）
                              + Learn 页能力轴卡片（SkillAxesCard）
AI 对话接口每次请求动态注入画像 / 进度 / 历史提问 / 复盘卡带来的案件上下文
```

**为什么诊断必须由规则产出**：同数据每次结论一致（演示可重放）、能回答"凭什么说他观察力弱"（指回具体轴与具体线索）、且模型无法编造案件里不存在的线索。LLM 只被允许改写标题这一句话，`findings` 与 `recommendations` 一律使用规则生成的原文本——**一旦让模型碰这些，它就会开始编「你忽略了手机短信」，而那个案件里根本没有短信**。

### 4.3 用户角色与权限设计

- 通过 JWT Token 认证，`requireAuth` 中间件校验登录态，`requireRole` 中间件校验角色权限
- 前端路由同样配置认证守卫，未登录自动跳转登录页，学生 / 教师路由互相隔离
- 学生通过邀请码加入班级，教师无法直接拉人

### 4.4 激励体系设计

- **经验值与等级**：闯关得分 ≥ 60 获得 XP，每 100 XP 升级，等级对应法律称号
- **按最佳成绩差额结算**：关卡与游戏案件都只按历史最好成绩结算，重复提交只补差额——既堵住"反复提交低分刷 XP"的漏洞，也不让认真重刷提高成绩的学生吃亏
- **顺序解锁**：主题内关卡按顺序完成，避免跳学，保证知识体系完整
- **成就徽章**：9 枚徽章覆盖起步、打卡、高分、通关等维度，仅在新解锁时播放庆祝动画
- **错题复习**：低分关卡进入待复习列表，鼓励巩固

### 4.5 内容设计思路

- **主题选择依据**：基于《中华人民共和国未成年人保护法》《预防未成年人犯罪法》等法律法规，结合青少年最常遇到的法律场景筛选
- **题目设计原则**：真实案例改编、语言适合中学生、情境题训练应用能力、每题附解析与法条出处
- **漫画内容**：校园欺凌、网络诈骗、消费者权益三个高频场景，读后展示"法律小课堂"
- **安全边界**：高风险场景（自伤、暴力、性侵、勒索）自动提示求助渠道（监护人 / 老师 / 110 / 12348）

### 4.6 AI 对话助手设计

- 基于 OpenAI 兼容接口（可切换 DeepSeek、小米 MiMo 等任意兼容模型），后端转发
- **带记忆**：每次对话注入用户画像、完成关卡摘要、历史提问，以及从复盘卡"追问"按钮带过来的案件与短板上下文
- **提示词约束**：不提供具体法律意见或办案结论，只做学习解释；涉及自伤、暴力、性侵、勒索等高风险内容优先建议立即求助；语言适合未成年人，不使用恐吓或刺激性描述；尽量给 3-5 条行动清单
- **防复述**：注入的用户上下文被显式标注"仅用于个性化回应，不要直接复述或逐条罗列"
- **三级降级**：未配置 API Key → 内置学习建议模板；上游返回错误 → 502 并提示；响应格式异常 → 兜底话术。**求助卡片由代码层拼接，三条降级路径里都一定出现**

### 4.7 风险预警架构

```
学生发消息 ──► POST /api/ai/chat
                 │
                 ├─ 同步窄规则 quickScreen()        ← 不调模型、不依赖 API Key
                 │     A 类自指危机表达 → 命中即高危
                 │     B 类歧义词 + 第一人称自指 + 无求知句式 → 命中
                 │     └──► 命中时在回复最前面强制拼接求助卡片
                 │          （110 / 12348 / 监护人与老师）
                 │
                 └─ 关键词预筛 isRiskCandidate()
                       │  取向与上者相反：要的是**召回**
                       │  （心理风险的主要形态没有硬关键词）
                       ▼
                 runRiskDetection()  ← fire-and-forget，绝不 await
                       │
                       ├─ 拉最近 3 条同 session 发言作为上下文
                       ├─ classifyWithModel()  temperature = 0
                       │     区分「描述亲身处境」与「了解法律规定」
                       ├─ crisis 命中时级别下限锁死 HIGH（模型无权降级）
                       ▼
                 recordRiskEvent()
                       │  同学生 + 同类型 + 24h 内 + 未处理 → 聚合累加
                       │  原句取"更严重的那个"，平级保留先出现的
                       ▼
                 notifyTeacher() → SSE 推送该班班主任
                       │  前端收到事件名后重新拉取列表（不维护两份状态）
                       ▼
                 教师端风险预警面板 → 填写沟通记录 / 标记已处理或误报
```

**两级判定的取向刻意相反**：窄规则决定"求助卡片出不出"，误报代价高，所以判得严；关键词预筛决定"这条值不值得花一次模型调用"，所以判得宽、宁可多捞一批交给模型去否掉。成本调节只调预筛列表，不动窄规则。

## 五、设计重点与难点

### 5.1 闯关系统的状态管理

- 后端通过 `UserProgress` 记录每名学生每关的最佳成绩与状态
- 顺序解锁逻辑在后端实现，前端根据 `progress` 字段渲染
- 答题在前端模态框内完成，提交时一次性校验，返回逐题解析

### 5.2 智能体画像的数据聚合与分析

- 画像引擎读取全部答题记录，按主题 / 题型聚合掌握度，近三个月与更早数据对比识别趋势
- 采用惰性更新（5 分钟缓存），控制计算开销，避免每次请求全量重算
- 结果持久化到 `StudentProfile` 表，前端雷达图纯 SVG 渲染，零第三方依赖

### 5.3 推荐与目标的规则引擎

- 推荐引擎综合画像薄弱主题、重复失败关卡、学习节奏、漫画阅读状态，生成带理由的推荐
- 目标引擎按周拆解并写入 `StudentGoal` 表，重复生成会先清理当周旧目标，保证唯一
- 全部离线计算，即使 AI Key 未配置，核心个性化能力依然完整可用

### 5.4 AI 助手的内容边界设计

- 系统提示词明确约束：不提供具体法律意见、高风险优先求助、语言适合未成年人、给出行清单
- 对话记录持久化到 `AiChatMessage`，用于个性化上下文（仅取最近 5 条），避免越权信息泄露

### 5.5 前后端认证与权限体系

- JWT + `requireAuth` + `requireRole` 双层校验
- 前端路由守卫 + 后端接口校验双重保障，防止越权访问

### 5.6 数据初始化与容器编排

- `start.sh` 容器启动时自动执行迁移与幂等 seed（`upsert`），首次启动即填充 60 关题库与测试账号，重复启动不产生重复数据
- 端口发布策略按用途区分，仓库内有两份 compose：
  - 根目录 `docker-compose.yml` 用于**本地开发**：db(3306) 与 backend(3001) 发布到宿主机，以便在宿主机运行 `npm run dev`（vite 的 `/api` 代理指向 `localhost:3001`）以及 prisma 命令直连数据库
  - `deploy/docker-compose.yml` 用于**部署**：仅前端 80 对外，db 与 backend 不发布端口，只在容器网络内可达（后端走 `db:3306`，前端 nginx 走 `backend:3001`），兼顾安全与端口冲突规避

### 5.7 能力轴的幂等重算

能力轴采用**从原始记录重算**而非提交时累加。累加会被重复提交和各处口径差异搞脏（同一局提交两次就多算一次样本），而重算天然幂等：数据源只有 `GameResult.detail` 与 `ComicRead.quizCorrect`，每个案件最多一条记录，重放多少次结果都一样。代价仅是每次多读约 10 行数据。

配套的两处口径设计：

- **`SkillAxis` 存计数而非百分比**——诊断必须区分"样本不足"和"掌握度低"。只玩过侦查的学生在「表达论辩」轴一条样本都没有，报 0 分既错误又打击人；百分比随时可算，**样本量算不回来**。
- **明细只描述最好那一局**——否则重玩一局打得更差会把能力轴拉低，**练习反而让画像变糟，说不通**。

### 5.8 客户端上报数据的信任边界

模拟法庭与案件侦查的判分逻辑与案件数据都在前端（约 190KB），服务端无法复算成绩。处理方式是把信任边界**只划一处**：

1. **形状与大小卡死**：客户端上报的单局明细用 zod 校验，`.strict()` 拒绝多余键，能力轴数组、漏项数组、标签长度、时长全部设上限，单条 JSON 约 8KB 封顶；
2. **只用于诊断**：该明细绝不参与 XP 结算，XP 仍只由 `score / maxScore` 驱动；
3. **结算侧另设防护**：完成度钳制到 `[0, 1]`、0 分不保底发放、按案件历史最好成绩只补差额。

这样"服务端无法验证分数是否真的打出来"这个残留问题的影响被限制在**每个案件只能拿一次**，不再是无上限膨胀。

### 5.9 实时推送的实现取舍

教师端风险预警采用 SSE 而非 WebSocket——这里是单向推送，SSE 够用且不引入新依赖。有一处必须自己实现：原生 `EventSource` 无法携带 `Authorization` 头，而本项目所有接口都走 Bearer token；把 token 塞进 URL 查询参数虽然能跑通，**但会让令牌进入 Nginx 访问日志**，因此改用 `fetch` + `ReadableStream` 手动解析 SSE 帧。

服务端每 25 秒发送注释帧心跳防止中间代理掐断空闲长连接，并显式关闭 Nginx 缓冲（否则推送会被攒着不发）；前端断线后 3 秒自动重连。推送只负责通知"有变化"，具体数据由前端重新拉取，**避免维护两份状态**。

### 5.10 交互性能的实测优化

前端若干处改动由 tracing 与实测数据驱动，而非凭感觉：

| 问题 | 实测数据 | 处理 |
|------|---------|------|
| 弹窗入场动画用缩放 | scale 版光栅化任务 16 个、峰值 4.3ms；位移版 11 个、1.3ms | 改为位移，视觉上的"抖"消失（看帧率看不出来） |
| 弹窗先开、内容后到 | 41ms 时被内容从 139px 撑到 499px，而动画有 400ms | 改为数据就绪再打开，动画跑在稳定布局上 |
| 通用 Markdown 解析器过重 | 正文最长 245 字符，62 篇里从未出现复杂语法；解析管线约 116KB，首次渲染阻塞主线程约 187ms | 自研极简解析器（源码约 3.2KB） |
| 推理模型逐字思考 | 一句话改写需 26 秒 | 关闭思考链后 0.7~1.5 秒；不认该参数的服务商自动摘掉重试 |

此外，路由级代码分割把 14 个页面拆成独立 chunk，静态案件与场景数据（约 4100 行）单独打包按需加载；图片资源全量 webp。

## 六、创新描述

### 6.1 「规则出结论，模型只出措辞」的诊断架构（核心创新）

传统普法教育"千人一面"，本项目通过内置的轻量智能体系统，让平台**认识每一个学生**：六维学习画像、六条能力轴诊断、智能推荐、错题复盘、每周目标、带记忆的 AI 对话。

其中最具特色的是诊断的生成方式：**学习诊断结论全部由确定性规则引擎计算，大模型只被允许把已算好的结构改写成一句话**。这一条边界带来三重收益：

- **可复现**——同一份数据每次诊断结果一致，演示可以重放；
- **可解释**——被问"凭什么说他观察力弱"，能直接指回是哪条能力轴、漏了哪条线索、属于哪一类；
- **不编造**——纯大模型诊断会说出案件里根本不存在的线索。**在教育产品里，编造结论不可接受。**

模型超时、报错、输出不合格三种情况一律退回模板文案，闭环在任何情况下都成立。**先让规则跑起来，再让 AI 开口。**

### 6.2 能力轴 × 主题轴的双坐标系学习闭环

主题轴管"去哪学"，**六条能力轴**（观察取证、信息获取、证据审查、逻辑推理、法律适用、表达论辩）管"诊断什么"——它们并非凭空设计，而是从模拟法庭与案件侦查**原本算完就弃的评分维度**收敛而来。

学生的每次操作变成细粒度信号（漏了哪条线索、漏的是哪一类证据、哪道题选错），信号变诊断，诊断变**可点击的推荐**（直接跳转到具体篇目或案件），新行为再回流成信号——**数据回流后诊断随之改变，闭环闭得上，且每一步都能现场演示**。

### 6.3 对话风险预警（教师端）

把"教师发现问题学生"从被动等待学生开口，变成系统主动预警：

- **两级判定，取向刻意相反**——窄规则决定"求助卡片出不出"（误报代价高，判得严），关键词预筛决定"值不值得花一次模型调用"（要召回，判得宽）；
- **救命的部分不依赖模型**——求助卡片由代码强制拼接，未配置 API Key 时也一定出现；窄规则命中即锁死 HIGH，模型无权降级；
- **针对普法场景专门优化**——学生在普法平台上经常在问法条、做假设推演，这是本场景特有的误报来源，判定提示词明确要求区分"描述亲身处境"与"了解法律规定"；
- **面向教师体验的聚合**——24 小时内同类风险聚合累加而非逐条新建，避免教师端被同一个名字刷满、反而导致整个预警面板被忽略。

### 6.4 互动形态与沉浸式体验

- **模拟法庭**：完整六阶段流程，全屏工作台呈现；
- **案件侦查的证据墙**：线索从"弹出小窗、看完就关"变成**永久留在墙上的一张卡片**，未发现的线索是位置固定的空卡槽——缺口比文字更刺激搜索欲。支持按证据类型筛选，让学生**在界面上自己先看见**"我收集的全是物证，一条电子证据都没有"，而这正是诊断引擎要指出的类型盲区；
- **普法漫画**：读后总结题的**正确答案必须能指回该篇漫画的具体一格**，答错时先引导学生回看那一格，而不是直接给答案。

### 6.5 智能体人格的统一

结算页复盘卡、侧边栏入口、AI 对话页统一为同一位「青知智能体」，共用名字与头像。此前这些位置各写各的、甚至叫不同名字，学生面对的是几个互不相干的 AI；统一之后，智能体**在结算页主动开口说话**，学生的心智变成"有一个老师一直跟着我"。

### 6.6 情境化题目设计

大量采用情境题（SCENARIO），模拟真实生活场景（如"同学在群里发布你的照片并配侮辱性文字"），考察的不只是法条记忆，更是真实场景中运用法律自护的能力。

### 6.7 双角色协同教学设计

学生自主探索 + 教师精准引导的教学闭环：教师建班、布任务、看数据、接收风险预警；学生闯关、游戏、问 AI，形成完整的"学习—练习—评估—干预"链路。

### 6.8 纯前端数据可视化

六维雷达图、能力轴卡片、7 日趋势图、场景平面示意图等全部手写 SVG，零第三方图表库依赖，包体更小、加载更快。

### 6.9 面向未成年人的体验细节

- **样本不足不报 0 分**——只玩过侦查的学生在「表达论辩」轴显示"样本不足"而非分数；
- **先肯定再指出短板**——诊断卡首条固定为强项确认，"只报忧是失败的产品"；
- **失败绝不伪装成功**——接口失败如实提示并给重试入口，不把一次网络失败渲染成"暂无错题，继续保持"；
- **过程内不给提示**——智能体只在结算时出现，否则学生不再自己推理、直接等喂答案，会污染诊断的数据源。

### 6.10 全栈 TypeScript 与工程严谨度

前后端全面 TypeScript + Prisma 类型安全 ORM，接口类型一致、查询结果明确、重构可控。关键设计取舍与踩坑记录直接写在代码注释中，与实现同处一地、不会随文档失效。

## 八、数据库设计

系统共包含 **19 个数据模型**、7 个枚举，共 32 处唯一约束与索引。

| 模型 | 说明 | 关键字段 |
|------|------|---------|
| User | 用户 | email, role, xp, level, grade |
| Class | 班级 | name, joinCode, teacherId |
| ClassMember | 班级成员 | classId, studentId |
| LearningUnit | 学习单元 | title, category, gradeRange, orderNo |
| Level | 关卡 | unitId, title, xpReward, orderNo |
| Question | 题目 | levelId, type, prompt, answerKey, explanation, difficulty |
| Attempt | 答题记录 | studentId, levelId, score, correctCount |
| **QuestionAnswer** | **逐题作答记录** | studentId, levelId, questionId, answer, correct |
| UserProgress | 学习进度 | studentId, levelId, bestScore, status |
| Resource | 普法资源 | title, type, tagsJson, contentMd |
| Assignment | 任务 | classId, targetType, targetId, dueAt |
| AssignmentSubmission | 任务提交 | assignmentId, studentId |
| ComicRead | 漫画阅读记录 | studentId, storyId, quizOptionId, quizCorrect |
| StudentProfile | 学生画像 | topicMasteries, weakAreas, strengths, learningStyle |
| AiChatMessage | AI 对话记录 | studentId, role, content, sessionId |
| StudentGoal | 每周学习目标 | targetType, targetCount, progress, completed |
| **RiskEvent** | **风险预警事件** | studentId, classId, kind, level, snippet, triggerCount, status |
| **GameResult** | **游戏单局最好成绩与明细** | studentId, gameType, caseId, bestPct, detail |
| **SkillAxis** | **能力轴累计计数** | studentId, axis, correct, total |

> 加粗的四张表是随「学生端改造」与「风险预警」两次迭代新增的，各自由一个版本化迁移引入（共 7 个迁移）。

**几处关键约束设计**：

- `UserProgress @@unique([studentId, levelId])`、`GameResult @@unique([studentId, gameType, caseId])`、`SkillAxis @@unique([studentId, axis])`、`ComicRead @@unique([studentId, storyId])`——这四个唯一键共同把"客户端反复提交"收敛为**幂等写入**，是差额结算与防刷分的地基；
- `QuestionAnswer` 逐题作答表——原先只存每关总分，导致错题复盘的题型正确率只能把错题数按题量平均分摊估算（5 题错 1~2 题则所有题型都算 100%，错 3 题以上则全部算 0%，阈值卡在 50%，与题型毫无关系）。补表后才真正可算；
- `SkillAxis` 存**计数而非百分比**——诊断必须区分"样本不足"和"掌握度低"，百分比随时可算，样本量算不回来；
- `RiskEvent` 的两个复合索引服务两条不同查询路径：`@@index([studentId, kind, status])` 服务 24 小时聚合去重，`@@index([status, lastSeenAt])` 服务教师端列表排序；
- `RiskEvent.classId` 刻意**不做外键**——学生退出班级后历史预警仍可查，符合"预警是留痕不是待办"的定位；
- **外键策略分两档**：学生私有数据全部级联删除，而教学基座（单元、关卡、题目、进度）改为 RESTRICT，防止删一个单元连带抹掉学生的答题历史。
