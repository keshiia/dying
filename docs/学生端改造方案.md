# 学生端改造方案

- **拟制日期**：2026-09-15
- **范围**：学生端「漫画学法 / 案件侦查 / 模拟法庭」三个模块的形态改造 + 智能体闭环打通
- **不在范围内**：教师端、学习闯关的答题逻辑、资源中心、任务中心
- **核实说明**：标注 ✅ 的结论我读过实际代码或用接口/脚本验证过；其余为设计提案

---

## 一、已确认决策与理由

> 这一节记录**为什么**，不只记录**是什么**。反面选项一并保留——三个月后这些理由比结论值钱。

### 1. 闭环类型：主动干预（B）

**结论**：智能体在结算节点主动给出诊断与可点击的下一步，而不是被动等学生来查。

**排除**：
- **数据闭环（A）**：把漫画/游戏行为灌进画像，学生仍自己去点。功能上是 B 的前提，但**看不见**——评委无法在 30 秒内感知到它。
- **对话闭环（C）**：只保留受约束的最小版本（推理阶段向智能体陈述思路）。不接 NPC 自由对话——不可控且会剧透。

### 2. 信号粒度：细粒度（B）

**结论**：记录**具体错在哪**——漏了哪条线索的 ID、哪个证人的秘密没问出、哪道题选错，而非只记维度得分。

**排除**：
- **粗粒度（A）**：只存六维/三维得分。与现有的 `bestPct` 没有代差，诊断说不出"你忽略了监控录像"这种能挂钩到具体资源的结论。
- **全埋点（C）**：加停留时长、翻页速度等行为日志。推得出"观察力弱"，推不出"忽略了电子证据"——而后者才是能路由到具体资源的钩子。

### 3. 坐标系：主题轴 + 能力轴

**结论**：主题轴（现有 6 大主题）管**去哪**；能力轴（6 条，从两个游戏的评分维度收敛）管**诊断什么**。

**排除**：只做主题轴——诊断粒度只能到"你网络安全弱"，无法解释为什么弱。

### 4. 漫画的角色：信号源（C₂）

**结论**：每篇漫画读完后加 **1 道总结题**，答对 +5 XP（保底 +10 不变），结果计入 `证据审查` 轴。

**排除**：
- **C₁ 漫画只是资源**：闭环退化为单向（侦查/法庭发现问题 → 漫画解释问题），漫画永远不进诊断。
- **把总结题出成知识题**：会与 303 道闯关题重叠。

**护栏（重要）**：漫画总结题的**正确答案必须能指回刚才那篇漫画里具体一格**（假鞋篇的答案能指回第 4 格"保留聊天记录、商品截图、实物照片"）；闯关题考的是**迁移**，答案不在任何看过的素材里。守住这条线，漫画就还是"读完了总结一下"，而不是"又做了一道题"。

### 5. 干预时机：结算页（折叠）+ Learn 页兜底

**结论**：主战场是**结算页**（法庭宣判 / 侦查告破 / 漫画读完），默认折叠成一行，学生主动点开才展开；Learn 页承接"没当场点开"的遗漏。

**排除**：
- **过程内提示（本次最重要的排除）**：学生一旦发现有提示可等，就不再自己推理，直接等智能体喂答案。**这会污染能力轴的数据源**——`🧩 推理答题` 和 `⚖️ 证据审查` 两个维度恰好是诊断的输入，喂答案等于自己毁掉自己的数据。
- **弹出式结算卡**：结算页现在是「案件告破！」的庆祝时刻。紧跟一张说"你漏了监控录像、连续三局忽略电子设备"的卡片，**等于在颁奖典礼上念检讨**。折叠而非打断，是青少年产品的体验底线。

### 6. 生成方式：规则出诊断，LLM 出措辞（C）

**结论**：规则引擎产出结构化诊断，LLM 只被允许把结构转写成一句话，**明确禁止引入结构中没有的事实**；模型不可用时降级为模板文案。

**排除**：
- **纯规则（A）**：演示时像一份报表。
- **纯 LLM（B）**：会编造案件里不存在的线索（例如说"你忽略了手机短信"，而该案件没有短信）。诊断层编造不可接受。

**三条理由**：① 可复现——同数据每次诊断一致，演示能重放；② 可解释——评委问"凭什么说他观察力弱"，能指回具体维度；③ 顺带接通一处已经断掉的线（见附录缺陷 4）。

### 7. 侦查形态：工作台（B）+ 现场示意图（C），路由级整页

**结论**：全屏暗色工作台，左案卷 / 中现场 / 右证据墙；**线索从模态框变成"钉在墙上的实物"**。

**排除**：
- **插画路线（A）**：`public/images/` 下只有 `comics/` 和 `banners/`，无任何场景插画。5 案件 × 3 场景 = 15 张图，且现有 `x/y` 百分比坐标是相对空盒子标定的，换插画后全部错位。
- **留在 AppShell 里只是变宽变暗**：旁边杵着一条亮色侧边栏，"沉浸"是假的。

### 8. 漫画全屏：一屏一格（A），路由 `/play/comics/:storyId`

**结论**：保持翻页逻辑，画幅放大到接近图片原始宽度，暗色背景，隐藏所有 chrome。

**排除**：
- **竖向条漫（B）**：素材是 6 张独立生成的图（高度各不相同：672 / 688 / 676 / 642），格与格之间没有视觉连续性，竖拼会露接缝；且 970px 的图在桌面全宽显示会糊。
- **全屏 overlay 而非路由**：智能体的推荐按钮需要**直接跳到某一篇**。「去看《买的球鞋是假货》」在模态框里做不到干净，在路由里是一行代码。

### 9. 位置交换：只换导航顺序（A）

**结论**：`AppShell.tsx` 里两行互换。

**说明**：侧边栏顺序**不等于**学生的第一眼——`/app` index 重定向到 `/app/comics`（`App.tsx:61`），学生登录先看到的是漫画墙。本次不新建首页（排除 C），因此"回访干预"落在 Learn 页。

### 10. 智能体身份：统一为「青知智能体」（A）

**结论**：结算卡、Learn 页画像/推荐、`/assistant` 对话助手共用一个名字与头像，学生的心智是"有一个老师一直跟着我"。

**排除**：保留两个 AI 人格（诊断是功能、对话是工具）——青少年用户会困惑，且诊断卡片可能让你"去问 AI 咨询助手"，形成套娃。

### 11. 法庭范围：数据改动必做 + 沉浸外壳（A+B）

**结论**：法庭必须产出六维明细（闭环绕不开它），并套同一套沉浸外壳；六阶段内部交互不动。

**排除**：完整工作台改造（C）——法庭 1027 行、六个阶段，比侦查还大。重做一遍不会多拿一分，但会让交付晚两周。

**附带收益**：法庭那份自绘弹窗（`Court.tsx:984-1020`）可直接删除换 `ui/Modal`——"去小窗"本来就要求把证据从模态里搬出来，搬完它就没用了。

### 12. 移动端：单栏 + Sheet 抽屉（A）

**结论**：桌面三栏；移动端中央现场占满屏，案卷与证据墙收进左右抽屉（复用已有的 `ui/Sheet`）。

**排除**：两套 UI 并存（C）——每处改动做两遍、测两遍，最终必然只有一套被维护。代码里已出现这个苗头（`ClueDetailModal` 与法庭自绘弹窗就是这么分裂出来的）。

### 13. 分档：P0 / P1 / P2（B）

**结论**：见第九节。关键调整：**LLM 措辞层从"必做"降到 P2**——规则诊断是那个 🅲 里的必需品，LLM 只是锦上添花，且它是唯一会现场翻车的一环。

### 14. 文档形态：工程向 + 决策理由节（A）

**结论**：本文件面向施工。参赛向材料由 `README.md` 承担（它已经是"作品简介 + 技术栈 + 许可证"的参赛结构），避免两份文档互相打架。

**默认假设**（如需变更请提出）：演示设备为投屏/桌面优先，移动端打磨排最后；不投入插画素材。

**这张图的关键在于它闭得上**：学生的行为变成信号 → 信号变诊断 → 诊断变推荐 → 推荐让学生产生新行为 → 新行为又变成信号。附录列出的 5 个缺陷里，有 3 个正好卡在这个环的几个接缝上，本次一并修掉。

### 闭环的可演示路径（P0 完成后）

1. 学生做「画室的神秘涂鸦」，漏掉 `走廊监控（周日录像）`（`digital` 类型）
2. 结算页出现折叠的一行：`🧠 青知智能体复盘：发现 3 个可提升点`
3. 点开 → 「你的**观察取证** 6/9，其中**电子类证据漏了 1 条**——你上一局也没查过手机/电脑」
4. 卡片里有一个按钮：`去看《天上掉馅饼？》`（按主题轴路由到 `网络安全` 漫画）
5. 学生点进 `/play/comics/comic-online-1`，读完答总结题
6. 回到 Learn 页，`证据审查` 轴的掌握度已经变了，推荐区不再推这篇漫画

**第 6 步是"闭环"的证据**——数据回流后诊断变了。

## 三、数据层

### 3.1 主题标签补齐（P0）

现状：**三个模块之间没有公共坐标系。**

| 模块 | 主题字段 | 实际取值 |
|---|---|---|
| 学习闯关 | `LearningUnit.category` ✅ | `校园法律 / 网络法律 / 家庭法律 / 消费法律 / 交通安全 / 禁毒法律`，经 `TOPIC_MAP` 归一为 6 大主题 |
| 漫画学法 | `ComicStory.topic` ✅ | `校园欺凌 / 网络诈骗 / 消费者权益` —— **与前两者都对不上** |
| 案件侦查 | 无 | — |
| 模拟法庭 | 无 | — |

漫画里写的 `校园欺凌` ≠ 画像引擎的 `校园安全`，`网络诈骗` ≠ `网络安全`。只有 `消费者权益` 撞对了。

**改造**：给三个模块的数据补一个 `topic` 字段，取值限定为 6 大主题之一，统一放在 `frontend/src/data/topics.ts` 作为单一事实源，避免第四次对不上。

### 3.2 六条能力轴（P0）

好消息：**这套轴不用新建，它已经写在两个游戏的评分函数里**，只是算完就扔了。

| 能力轴 id | 显示名 | 汇聚自 | 现有代码位置 |
|---|---|---|---|
| `OBSERVE` | 观察取证 | 侦查 `🔍 线索搜集` ＋ 法庭 `🔍 现场搜证` | `Detective.tsx:79`、`Court.tsx:54` |
| `INTERVIEW` | 信息获取 | 侦查 `💬 询问证人` | `Detective.tsx:83` |
| `EVIDENCE` | 证据审查 | 法庭 `⚖️ 证据审查` ＋ **漫画总结题** | `Court.tsx:62` |
| `REASONING` | 逻辑推理 | 侦查 `🧩 推理答题` | `Detective.tsx:91` |
| `LAW` | 法律适用 | 法庭 `📜 法条适用` ＋ `⚖️ 裁决` ＋ `📋 处分措施` | `Court.tsx:79-92` |
| `ARGUE` | 表达论辩 | 法庭 `💬 法庭辩论` | `Court.tsx:73` |

**已知的空心轴**：`INTERVIEW` 只有侦查贡献，`ARGUE` 只有法庭贡献，`EVIDENCE` 只有法庭 + 漫画。也就是说——**只玩过侦查的学生，`ARGUE` 上永远是 0 分**。诊断引擎必须把"样本不足"和"掌握度低"分开，否则会给学生报"你的表达论辩能力 0 分"这种既错误又打击人的结论。

### 3.3 Schema 改动（P0）

```prisma

  studentId String

  detail    Json?

  updatedAt DateTime @updatedAt
  // ...原有索引与唯一约束不变
}

// 2) 漫画阅读：加总结题结果
model ComicRead {
  id           String   @id @default(cuid())
  studentId    String
  storyId      String
  // 新增：总结题作答。未作答时为 null
  quizOptionId String?
  quizCorrect  Boolean?
  createdAt    DateTime @default(now())
  // ...原有约束不变
}

// 3) 新增：能力轴快照，供 Learn 页与诊断引擎读取
model SkillAxis {
  id        String   @id @default(cuid())
  studentId String
  axis      String   // 'OBSERVE' | 'INTERVIEW' | ... 
  correct   Int      @default(0)
  total     Int      @default(0)
  updatedAt DateTime @updatedAt

  student   User     @relation(fields: [studentId], references: [id], onDelete: Cascade)

  @@unique([studentId, axis])
  @@index([studentId])
}
```

> `SkillAxis` 用**累计计数器**而不是百分比，因为诊断需要"样本量"来判断可信度（见 3.2 的空心轴问题）。百分比随时可算，样本量算不回来。

### 3.4 `detail` 字段的结构与校验（P0，安全相关）

`detail` 由前端上报，**服务端无法复算**（判分逻辑和案件数据都在前端，`student.ts:598-600` 的注释已承认这一点）。因此必须做**形状与大小双重校验**，否则这是一个可以塞任意 JSON 的口子：

```ts
// 侦查
const DetectiveDetailSchema = z.object({
  v: z.literal(1),
  missedClues: z.array(z.string().max(64)).max(60),      // 5 案最多 51 条线索
  missedClueTypes: z.record(z.enum(['physical','digital','testimony','observation']), z.number().int().min(0).max(60)),
  npcSecretsMissed: z.array(z.string().max(64)).max(30),
  deductionWrong: z.array(z.string().max(64)).max(20),   // 每案 4 题
  durationMs: z.number().int().min(0).max(6 * 60 * 60 * 1000),
}).strict()

// 法庭
const CourtDetailSchema = z.object({
  v: z.literal(1),
  missedHotspots: z.array(z.string().max(64)).max(40),
  evidenceWrong: z.array(z.string().max(64)).max(30),
  debateWrong: z.array(z.string().max(64)).max(20),
  lawWrong: z.array(z.string().max(64)).max(20),
  verdictWrong: z.boolean(),
  penaltyWrong: z.boolean().optional(),
  durationMs: z.number().int().min(0).max(6 * 60 * 60 * 1000),
}).strict()
```

`.strict()` 拒绝多余键，`.max()` 卡住数组长度——单条 JSON 上限控制在约 8 KB。

**信任边界说明**：这不引入**新的**信任问题，只是把已经被信任的那条路上多传一点东西。但既然要做，就顺手做对：`detail` 只用于**诊断**，**绝不参与 XP 结算**（XP 仍只由 `score/maxScore` 驱动，保持现有的 clamp + 最好成绩差额逻辑）。

## 四、诊断引擎

**新增文件**：`backend/api/lib/agentDiagnosis.ts`（与 `studentProfile.ts` 同构，约 200 行）

### 4.1 输入与输出

```ts
export type Intervention = {
  agent: '青知智能体'
  headline: string          // 一句话诊断（LLM 可改写，也可模板兜底）
  findings: Finding[]       // 折叠后展开，最多 3 条
  recommendations: Rec[]    // 最多 2 条，每条带可跳转路由
  degraded: boolean         // 是否走了模板兜底（前端据此淡化"智能"表述）
}

type Finding = {
  axis: AbilityAxis
  kind: 'SINGLE' | 'PATTERN' | 'CROSS_MODULE' | 'STRENGTH'
  text: string
  evidence: string          // 必须指回具体线索 id / 题目 id 的可读名
  crossCase?: string        // 跨局关联的说明
}

type Rec = {
  kind: 'COMIC' | 'COURT' | 'DETECTIVE' | 'LEVEL'
  targetId: string
  label: string
  reason: string
  to: string                // 可直接 navigate 的路由
}
```

### 4.2 规则（确定性，可复现）

| # | 规则 | 触发条件 | 产出 |
|---|---|---|---|
| R1 | 单局弱项 | 某轴本局得分率 < 60% 且 `total >= 3` | `SINGLE` finding，`evidence` 指向漏掉的具体线索名 |
| R2 | 类型盲区 | `missedClueTypes` 中某类型 ≥ 2 条未发现 | `PATTERN` finding：「你漏了 N 条电子类证据」 |
| R3 | 跨局重复 | 同一轴在最近 3 局中 ≥ 2 局 < 60% | 升级 `urgency`，并加 `crossCase`：「连续 2 局……」 |
| R4 | 跨模块呼应 | 弱项轴 = `EVIDENCE` 且该主题漫画未读 | `CROSS_MODULE` finding + 漫画推荐，路由 `/play/comics/:storyId` |
| R5 | 强项确认 | 某轴本局 100% 且 `total >= 3` | `STRENGTH` finding（**正反馈必须占一席**，不能只报忧） |
| R6 | 样本不足 | 某轴 `total < 3` | **不产出 finding**，不显示 0 分（见 3.2 空心轴） |

**排序与去重**：`STRENGTH` 优先展示（先肯定）；`findings` 最多 3 条，同轴只留一条，`PATTERN`/`CROSS_MODULE` 优先于 `SINGLE`。

### 4.3 LLM 层（P2）

- 只接收去掉 id 的 `Intervention` JSON，**只允许改写 `headline`**，`findings[].text` 与 `recommendations[].reason` 一律用规则生成的原文本。
- 系统提示中明确："仅可改写措辞，**不得引入未提供的事实、线索名或数字**"。
- 调用失败 / 未配置 key / 超时 3s → `degraded = true`，回退到模板 headline。**闭环在任何情况下都成立**（复用 `ai.ts:92-112` 的既有兜底模式）。

### 4.4 触发方式：搭在现有结算接口上（不加往返）

`settleGameResult()`（`student.ts:619-657`）已经在事务里读了本局与历史成绩。把诊断挂在这里，**在同一次响应里返回 `intervention`**：

```ts
// student.ts 的 /detective-result 与 /court-result 响应增加一个字段
res.json({ success: true, xpGain, user, intervention })
```

**零额外延迟、零额外请求。** 漫画侧同理，`/comic-read` 的响应带上 `intervention`。

## 附录：本次排查发现的问题

> 标注 ✅ 的已核实。这些是既有缺陷，不是本方案引入的；其中 3 个正好卡在闭环的接缝上。

### 缺陷 1 ✅ 「推荐模拟法庭」永远触发

`recommendationEngine.ts:147`

```ts
const hasCourtRecently = recentAttempts.some((a) => a.levelId.startsWith('court-'))
```

但关卡 id 的格式是 `level-{slug}-{orderNo}`（`prisma/seed.ts:825`），**不存在 `court-` 前缀**；且模拟法庭/案件侦查根本不写 `Attempt` 表（它们写 `GameResult`）。

**后果**：`hasCourtRecently` **恒为 false** → 不论学生刚玩过多少次法庭，推荐区永远挂着「试试模拟法庭游戏」。

**修复**：改查 `GameResult` 表（`gameType: 'COURT'`，近 7 天）。

### 缺陷 2 ✅ 漫画"已读"检查永远不命中

`recommendationEngine.ts:162-166` 的 `comicMap` 用的是：

```ts
'校园安全': { id: 'campus',   title: '「校园欺凌」普法漫画' },
'网络安全': { id: 'network',  title: '「网络诈骗」普法漫画' },
'消费者权益': { id: 'consumer', title: '「消费者权益」普法漫画' },
```

而 `Comics.tsx:127-130` 上报的 `storyId` 是 `comic-bullying-1` / `comic-online-1` / `comic-consumer-1`。

**后果**：两个 id 空间完全对不上 → `comicRead.findUnique({ storyId: 'campus' })` 永远查不到 → **已读判断永远为"未读"，反复推荐学生已经读过的漫画**。且 `targetId: 'campus'` 在前端无法路由到任何东西。

**修复**：`comicMap` 改用真实 `storyId`，并随 3.1 的主题标签统一。

### 缺陷 3 ✅ 漫画推荐无法定位到具体篇目

`RecommendationSection.tsx:88-89`：

```ts
} else if (rec.type === 'COMIC') {
  navigate('/app/comics')      // 只到列表
```

**后果**：推荐说「建议阅读网络诈骗漫画」，点进去是一个 3 篇的列表，学生要自己找。推荐的说服力损失在这一步。本次的 `/play/comics/:storyId` 路由修复它（见 8.3）。

### 缺陷 4 ✅ AI 的 `context` 字段解析后从未使用

`ai.ts:15-22` 定义：

```ts
context: z.object({
  unitId: z.string().optional(),
  levelId: z.string().optional(),
  resourceId: z.string().optional(),
}).optional(),
```

`ai.ts:31`：`const { message, sessionId } = parsed.data` —— **`context` 被解析完就扔了**，从未进入 `userContext` 或系统提示。

**后果**：上下文注入这条线是留了口子没接线。智能体的「追问」按钮要把诊断结构带进对话，正好走这条路（决策 6）。

### 缺陷 5 ✅ NPC 位置三处并存，数据侧为空

| 位置 | 内容 |
|---|---|
| `DetectiveNpc` 类型（`detectiveCases.ts:38-39`） | 声明了 `x?: number; y?: number` |
| 案件数据（15 个 NPC） | **0/15 填了坐标**（已核实） |
| `Detective.tsx:44-65` | `NPC_POSITIONS` 硬编码 15 组坐标，UI 实际读这一份 |

另有一个遗留的一次性脚本 `frontend/src/data/add-npc-pos.cjs`，目的正是"把坐标写进案件数据、删掉硬编码常量"，但**产出未落地**；且它按 `"id": "npc-x"`（带引号）查找，对案件 4/5 使用的 `id: "npc-x"`（不带引号）写法会失效。

**修复**：坐标统一移入 `sceneMaps.ts`（见 5.4），删除 `NPC_POSITIONS` 与 `add-npc-pos.cjs`，`DetectiveNpc` 的 `x/y` 字段一并移除。

### 缺陷 6 ✅ 两份功能重复的模态框

**修复**：随 7.3 一并删除。
